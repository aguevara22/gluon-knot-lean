# Automatic execution rule for proof work

Reassess the strategy automatically when substantial work produces no newly
completed original source claim. Preserve the source, acceptance requirements,
and all accepted declarations.

## Automatic reassessment

Before starting another work batch or assigning construction to an agent, and
at every progress report, check progress toward the current source claim.

Reassess automatically after **two substantive attempts or 60 minutes of active
work without a new accepted source claim, whichever comes first**. Count serious
construction, reasoning, and debugging attempts, not individual tactic/compiler
retries. Track elapsed active work across collaborators without double-counting
simultaneous time; exclude pauses and unattended waits.

Reassess immediately on a domain mismatch, circular dependency, impossible
interface, repeated failure of the same method, or growing helper scope without
a demonstrated route to the source conclusion.

Only a newly accepted original source claim resets acceptance stagnation.
Definitions, helper lemmas, compiler successes, packets, reviews of fragments,
agent changes, and renamed strategies do not reset it. Record a complete
kernel-proved source claim separately: if only acceptance is delayed, diagnose
the review/acceptance bottleneck instead of discarding a valid proof.

## Required response to a trigger

Pause further expansion of the current construction and perform a bounded
method audit without waiting for the user to intervene:

1. Restate the exact source claim, remaining claim-critical obligation, and
   required domains/interfaces. Identify which results actually compose.
2. Diagnose whether mathematics, representation, decomposition, tools, review,
   or execution control is blocking progress. Check whether an assumed bridge
   merely restates the desired conclusion.
3. Compare continuing, changing method/representation, and abandoning the
   failed route. Choose using mathematical evidence. A viable long proof may
   continue, but helper counts alone do not justify that choice.
4. Specify one decisive next test with exact inputs and target, success
   criterion, an explicit effort bound no longer than the next audit window,
   and a consequence if it fails. Label unproved feasibility **CONJECTURE**.
5. Record the decision and report that the accepted claim count is unchanged.

Check again when that test finishes, fails, or exhausts its bound, before
authorizing more construction. Retain cumulative stagnation history after an
audit; a new bounded window is not a new accepted claim. Do not weaken claims,
alter denominators, or reclassify helpers to manufacture progress.

## Resume state

Read the project's saved execution state and its latest strategy audit before
resuming construction. Record the current source claim, accepted count,
complete-but-unaccepted source claims, attempted critical obligation, active
effort, audit trigger, decision, and next test in the working state.

If previous effort is unknown but substantial stalled work is evident,
reassess rather than assume a fresh budget. Changing agents, starting a new
session, or resuming after a pause does not reset acceptance stagnation.
